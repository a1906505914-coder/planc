## 一、项目是什么（30 秒版）

**一套把"账套原始数据 → 审计底稿"全流程自动化的 Python 小程序集**，用于替代人工从 TB/GL 逐科目编制底稿的工作。

| 维度 | 现状（截至 2026-08-30） |
|---|---|
| 程序规模 | **201 个 Python 脚本** + 模板/配置/文档，已纳入 Git 仓库 |
| 科目生成器 | **13 个主科目生成器**（往来/银行/税费/薪酬/费用/损益/存货/长期资产/借款/权益/研发/收入/营业外） |
| 目标底稿 | 49 张科目底稿（13 builder × 49 科目），按"往来对象 / 原值折旧 / 余额 vs 发生额 / 附注模板"四特征分类 |
| 覆盖体系 | **双线**：SAP 体系（AH 集团 88 实体、ADF 3300/3400 等）+ U8 体系（XBJ 建筑集团 201 实体、AYL 18 家、AJ/ga 40 家、国开行 6100 等） |
| 质量闸门 | 三件套审查（audit_checker + self_check + recon_self）+ 指纹回归 + 完整性总表 |
| 数据安全 | 本地先行脱敏（Desensitizer / mask 引擎），真实主体名称不进 AI 对话 |

**核心理念（用户定调，不可妥协）**：底稿质量第一——TB 控制数一致、勾稽四段对平、明细到末级、表表一致、audit_checker ERROR 0 才交付；接入速度第二——在不牺牲质量前提下，新账套接入向"<5 分钟（已知形态）"目标收敛。

## 二、设计架构

### 2.1 总览：六层管道（现行总纲）

```
┌────────────────────────────────────────────┐
│ ① 摄取 Ingest        源文件 → 原始行 · 契约校验 │  ← 方言入口①
├────────────────────────────────────────────┤
│ ② 标准化 Normalize   方言/列序/科目码 → 标准科目 │  ← 方言入口②
├────────────────────────────────────────────┤
│ ③ 校验 Validate      TB 控制数核对 · Fail Fast │
├────────────────────────────────────────────┤
│ ④ 计算 Compute       生成器产【结构化数据】      │  ← 业务代码只认标准科目
├────────────────────────────────────────────┤
│ ⑤ 渲染 Render        模板 → Excel             │  ← 单体模板 / 合并模板 / 附注模板
├────────────────────────────────────────────┤
│ ⑥ 审计检查 Audit     audit_checker + 回归闸门  │
└────────────────────────────────────────────┘
  横切：元数据层（账套档案/科目映射/模板描述）· 任务编排（内存预算/断点续跑）
```

核心决策：**"计算"与"呈现"分离，呈现层模板化**——一个科目 = 一份结构化数据 + 多份模板输出（单体一份、合并一份、附注一份）。排版优化、单体/合并差异化、架构升级、质量验证四个方向都落在这一个决策上。

### 2.2 数据接入层（① ② ③）

- **统一接口**：`ledger_backend.py` 定义 LedgerBackend 接口（read_tb / discover），下挂 U8 / SAP300 / AH 三种后端；读取差异在接口层收敛。
- **SAP 适配三层链路**（SAP 体系取数铁律）：
  1. 结构解析（文件/表头/期间）
  2. 数据清洗（列映射、指令号列、缓存瘦身 .pklz）
  3. 口径归一化（科目内部码方言、功能范围拆分、期间口径）
- **账套档案（元数据层）**：`account_profiles.json` 扩展登记每账套的数据形态/科目码映射/列映射/币种/期间口径——**新账套只登记不写代码**（目标）。
- **Fail Fast**：TB 控制数 vs 标准化 GL 在 ③ 层立即核对，勾稽四段不过即中止，绝不带病下传。
- 已统一的先例：`ledger_backend`（读取）、`cache_manager`（缓存）、`desensitizer`（脱敏）、`special_reviews.REGISTRY`（专项编排插件式注册）。

### 2.3 计算层（④）

- 生成器只产出**结构化结果**（审定表/明细表/附注/抽凭的数值形态），不含样式；科目口径内建断言（生成时校验"控制数 = Σ明细"）。
- 合并专属数据在此层计算：内部交易配对（往来互抵 / 购销抵消 / 资金池上下划拨）。
- 已预留中间层：`audit_result_export.py`（审定数 → 结构化 JSON，`adjustments` 参数已预留）、`audit_protocol.py`（底稿行类型协议）。

### 2.4 渲染层/模板体系（⑤）

- **模板 = 布局 + 样式 + 规则**：双行表头 / 分组底色 / 合并列强化 / 零值留空 / 冻结——已完成的排版规则沉淀为模板默认样式。
- 三类模板：**单体模板**（客户级明细/账龄/抽凭/对方科目核对）、**合并模板**（横展式：行=项目末级 × 列=各单体+集团合计+抵消借/贷+合并数 + 内部交易抵消核对）、**附注模板**（列=主体+合并 4 行）。
- 渲染层：`xw_render.py`（xlsxwriter 流式渲染，避免 openpyxl 逐 cell 大表 OOM）。

### 2.5 质量体系（⑥ + 横切）

| 机制 | 程序 | 作用 |
|---|---|---|
| 三件套审查 | `audit_checker.py` / `self_check.py` / `recon_self.py` | 事后检查 + 底稿 vs 自建 TB 同源核对 |
| 指纹回归 | `working_paper_fingerprint.py` + `regress_module.py` / `regress_all.py` | 改代码前后指纹对比，任何内容差异即报 |
| 完整性总表 | `wp_completeness_check.py` | 一键扫全部底稿，每底稿一行（关键表数/空表/ERROR/WARN/状态） |
| 运行报告 | 自动写 `run_history/run_{时间}.md` | 每份底稿可追溯"哪个版本代码 + 哪批数据"生成 |
| 断点续跑 | 自动（`.resume_{主体}.jsonl`） | 大任务崩溃后重跑自动跳过已完成且签名未变项 |
| 看门狗 | `watchdog_check.py` / `long_task_guard.py` | 长任务心跳停滞超 30 分钟告警 |
| 运行前自检 | `preflight_check.py` | 磁盘空间/文件占用/并发/数据完整性，BLOCK 阻断 |

**核验方法论铁律**：先单体 TB 核验，再上升合并；标准流程 = 收账套 → 程序自建 TB → 生成全部底稿 → 与自建 TB 核对（diff=取数 bug）→ 用户提供 TB 交叉核对。损益科目 TB 净额=GL 净额可直接取数；往来款科目需凭证级处理。

### 2.6 统一证据链路（外部证据 → 科目底稿）

```
外部证据（合同 / 询证函回函 / 银行流水 / 保函）
  → 统一识别层（OCR：tesseract → RapidOCR 升级中，处理扫描件/微信图片）
  → doc_type 路由（doc_router.py）
  → 对应科目底稿（银行 → 货币资金、函证 → 往来、合同 → 借款/收入…）
```

支撑程序：`contract_ocr_batch.py` / `confirm_parse_all.py` / `bank_statement_parser.py` / `ocr_bank_hd.py` 等，92 份合同 + 91 份函证回函已完成 OCR 处理。

### 2.7 数据安全（横切，铁律）

- **本地先行脱敏**：所有数据进 AI 对话前先本地脱敏（`desensitizer.py` + `mask_engine.py` / `mask_gate.py` / `mask_batch.py`），真实主体名称永不进入对话；`mask_dict.json` 维护掩码字典，confirm/contract 语境隔离。
- 底稿交付按 XBJ 标准：微软雅黑 10 / Times New Roman 10pt、头部 DDEBF7、细边框、数字格式 #,##0.00、合计行仅汇总数值列（禁止虚假求和）。

## 四、运行方式（快速上手）

| 方式 | 命令 | 适用 |

| 一键全套 | `run_audit.bat run_all.py ah`（AH 三集团并行）<br>`run_audit.bat run_all.py <数据包目录>` | 日常全套生成 |

### 5.2 已预留设计（契约已定，实现后补）

- **六阶段流水线**：`regen_all` = ① self_tb_gen ✅ → ② 13 builder ✅ → ③ recon_self ✅ → ④ reclass_gen（重分类调整，JSON 契约已定）→ ⑤ report_gen（合并试算表/报告，offset.json 人工维护）→ ⑥ recon_ext（外部数据核对，统一差异 JSON 契约已定）。安全边界：调整分录只产"建议"，人工确认后才生效。
- **抽样规模自动计算**：`audit_sampling.py` 预留（OM/PM/SAD/风险等级 → 最低样本量 n，大额必抽 + 随机补足），接入点 = `audit_shell.finalize_workbook` 统一注入。
- **契约库（形态地图）**：每接入一个新账套形态，契约沉淀进账套档案库，越用越全；目标接入耗时——已知形态 <5 分钟、已知软件新变体 <30 分钟、全新软件形态 <2 小时。

## 六、多人共享协作架构（团队如何共同推动这套程序）

### 6.1 总体架构：服务器 = 文件柜 + Git 仓库，计算在各人本机

```
┌────────────────── 服务器 / 共享源头（如本机或 NAS）──────────────────┐
│  Git 仓库（程序唯一真身：201 脚本 + 模板 + 配置 + 文档）                │
│  共享数据盘（账套原始数据：科目余额表/综合查询明细表/网银 CSV/OCR 产物）  │
│  共享产出区（正式底稿/报告，按账套×年度分目录）                         │
└──────────────────────────────────────────────────────────┘
        ↑ clone/pull          ↑ 只读挂载           ↑ 写回/同步
   成员 A 本机            成员 B 本机            成员 C 本机
   WorkBuddy 读本机副本    直接读服务器数据       结果写共享区/云盘
```

**关键认知**：
- 程序和数据只有一个**真身**（服务器）；每人的 WorkBuddy 日常读写的是"本机上的副本 + 服务器上的数据"。
- **计算发生在各人本机**——66 万行序时账、1300 万行 SAP txt 都在"接手任务那个人"的机器上跑，服务器只做文件/Git 服务，性能负担轻（千兆网传 2GB 约 20~30 秒）。
- 本机当服务器完全可以起步（验证流程 > 追求性能），出现多人并发大任务排队、需 7×24 常开、数据量再上量级时，再升级 NAS/云服务器——Git 仓库整体搬走即可，迁移平滑。

### 6.2 Git 协作流程（同时优化同一程序的标准做法）

```
Git 服务器主分支（唯一权威）
   ├─ 成员 A 分支：改取数层（sap_adapter / ledger_backend）
   ├─ 成员 B 分支：改生成器（13 builder / 渲染层）
   └─ 成员 C 分支：改核验（checker / 回归 / 完整性）
         ↓ push
   合并审查（PR / 人工复核）→ 合入主分支 → 全员 pull 拿到合并结果
```

**三条铁律**：
1. **按模块/文件分工**（A 改 adapter、B 改 builder、C 改 checker），文件级并行零冲突；真冲突只发生在"同一文件同一段"——Git 用 `<<<<<<< HEAD / ======= / >>>>>>>` 标记，人工决策保留哪边或融合。
2. **绝不两个实例同时写同一个本地/共享文件**（last-write-wins 会互相覆盖）；同一文件改动走"提交 → 合并"，不直接并发写。
3. **合并必经审查**，且合入前跑三件套（audit_checker + self_check + recon_self）+ 指纹回归，防"一人改全局崩"。

**冲突合并五步**：`git pull` → 看标记定位冲突文件 → 人工合并（保留你的/保留对方的/融合）→ `git add + commit` → `git push`。冲突不是错误，是"文件被无声覆盖"变成了"摆在明面上的选择"，且 `git log` 全程可追溯（天然审计留痕）。

### 6.3 分工与角色建议

| 角色 | 职责 | 对应程序域 |
|---|---|---|
| 架构/取数负责人 | 读取层、账套档案、新账套接入 | `ledger_backend` / `sap_adapter` / `account_profiles` |
| 生成器负责人 | 科目底稿、模板、渲染层 | 13 builder / `xw_render` / `audit_templates` |
| 质量负责人 | 三件套、回归、完整性、防回退 | `audit_checker` / `regress_*` / `wp_*` |
| 专项核对负责人 | 银行/函证/合同/关联往来/账龄 | `bank_*` / `confirm_*` / `contract_*` / `ah_intra_*` |
| 数据安全负责人 | 脱敏、掩码、权限、共享盘管理 | `desensitizer` / `mask_*` |

### 6.4 数据与结果共享规则

- 源数据只读挂载服务器共享盘，**不复制到各人本机**（省空间、永远最新）；
- 结果默认产在各人本机，三种方式让全组可见：**直接写共享产出区**（按账套×年度子目录，避免两人写同一文件）/ **本机 + WPS 企业云盘同步**（半成品不污染共享区）/ **两阶段**（本机生成 → 人工核对 → 传共享，最贴合审计流程）；
- 大任务（全量重跑）**串行执行**，避免并发写文件损坏；并发只发生在互不干扰的专项核对。

### 6.5 团队规范（加入即遵守）

1. 一律经 `run_audit.bat` 运行（行序稳定）；
2. 改代码前 `git status` / 改后跑指纹回归；重跑期间不改代码；
3. 提交信息写清楚"改了什么 + 为什么"（可追溯）；
4. 数据安全红线：**所有数据进 AI 对话前本地脱敏**，真实主体名称永不进入对话；
5. 发现数据/工具问题在底稿中如实标注（禁止"报正常"），差异项标人工复核，不自动归一化。

### 6.6 协作规范补充（P1/P2 落地，2026-08-30）

| 规范 | 约定 |
|---|---|
| **环境一致性** | 新成员 4 步：`git clone` → `python -m venv .venv` + `pip install -r requirements.txt`（依赖已锁版本）→ 设 `AUDIT_DATA_ROOT`（+ 可选 `AUDIT_CACHE_DIR`/`AUDIT_GL_CACHE_DIR` 指本地缓存）→ 经 `run_audit.bat` 运行（详见 README §七） |
| **输出归属** | 结果写共享产出区时按"账套×年度×生成者"子目录分工，避免两人写同一文件；`run_history` 定期同步共享区（每份底稿可追溯谁、哪个 commit、哪批数据） |
| **指纹基线谁更新** | 基线（`_wp_fingerprint_base.jsonl`）**只由合并审查者**在改动验证通过后更新，其余人 `check` 全红 = 提醒"基线待更新"而非自行改动 |
| **回归前置** | 合并分支进主分支前，必须跑 `regress_module.py` 对应模块 + 指纹回归；批次级改动走 `run_all.py` 自动回归闸门 |
| **定时任务单主** | WorkBuddy 定时任务（Automations）**单主负责制**：一个账套的定时任务只由一人配置，避免多人重复触发同一数据包（同包并发已被 `.audit.lock` BLOCK 兜底） |
| **数据版本化** | 源数据更新（企业重导）后，先清 `.cache`/`.gl_cache`（或设 `AUDIT_NO_CACHE=1`）再重跑；缓存 key 已含文件签名，源文件 mtime/size 变化自动失效 |
| **断点续跑留痕** | `.resume_{主体}.jsonl` 记录含 host 字段（哪台机器写的）；跨机续跑安全（签名校验兜底，签名变自动全量） |
